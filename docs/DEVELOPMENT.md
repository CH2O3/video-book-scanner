# 開発者向けの説明

使い方は [README](../README.md) を見てください。ここには、処理の仕組み、コマンド、評価と試験の結果をまとめています。

## コマンドライン

```bash
vbs scan 動画.mp4 [動画2.mp4 ...] [--rtl] [--single] [--expected-pages 220] [--ui]
vbs status プロジェクト
vbs ui プロジェクト
vbs run プロジェクト
vbs export プロジェクト [--force]
vbs choose / include / exclude / ack / gutter ...   # 確認画面と同じ操作
```

`vbs` は `.venv\Scripts\vbs.exe` にあります。`python -m vbs` でも起動できます。

## 画面のAPI（AIエージェントや自動化から操作するとき）

`VideoBookScanner.bat`（`vbs ui`）が開く画面は、`127.0.0.1` だけで待ち受けるHTTPサーバーです。黒い画面に出るアドレス `http://127.0.0.1:<ポート>/#t=<トークン>` のトークンを、ヘッダー `X-Token: <トークン>`（または `?t=<トークン>`）で付けて呼びます。画面が開いている間はプロジェクトがロックされるので、`vbs` コマンドや `project.json` の直接編集ではなく、このAPIを使ってください。

### 読む

| 要求 | 返すもの |
|---|---|
| `GET /api/state` | プロジェクト全体（`project`：区間 `segments`、フレーム `frames`、ページ `pages`、出力順 `order`）、要確認の一覧 `review`（`id`・`codes`・`labels`）、理由コードの表示名 `labels`、未反映のページ `pending`、見開きごとの補正 `page_options` |
| `GET /api/job` | 処理の状態（`running`・`stage`・`frac`・`msg`・`error`・`result`） |
| `GET /files/<プロジェクト内の相対パス>` | ページ画像（`pages[].image`）、候補フレーム（`frames[].path`）、縮小画像（`thumb`）、OCRの文字（`pages[].ocr.txt`）など |
| `GET /api/page_view?pid=<ページID>&mode=final\|plain\|frame&w=1400` | 仕上がり／補正前（切り抜きだけ）／元の映像（紙の範囲と分割線つき）のJPEG |
| `GET /api/preview?video=<動画ID>&time=<秒>&step=<±コマ数>&w=1280` | 動画のその時刻（から step コマ動いた）フレームのJPEG。実際の時刻はヘッダー `X-Frame-Time` |

ID の形：区間 `s0001`、ページ `s0001-L` / `s0001-R`（1ページずつのときは `-S`）、フレーム `f0001`、動画 `v0001`。

### 直す（`POST /api/action`、本文はJSON。成功すると新しい状態を返す）

| `op` | 内容 | 例 |
|---|---|---|
| `choose` | 区間の候補を替える | `{"op":"choose","segment":"s0012","frame":"f0034"}` |
| `include` | ページ・区間を使う／使わない。区間を `true` にすると「未採用の区間」を採用する | `{"op":"include","id":"s0042","value":true}` |
| `ack` | 要確認を「確認済み」にする | `{"op":"ack","id":"s0098-L"}` |
| `add_frame` | 動画の任意の時刻のフレームを、その区間の候補に加えて使う | `{"op":"add_frame","video":"v0001","t":244.37,"segment":"s0099"}` |
| `geometry` | 紙の範囲と分割線を手で指定する（元フレームの画素座標、分割線はフレーム幅に対する割合） | `{"op":"geometry","segment":"s0214","bbox":[270,140,3060,2120],"gutter_ratio":0.447}` |
| `clear_geometry` | 手の指定をやめて自動に戻す | `{"op":"clear_geometry","segment":"s0214"}` |
| `page_options` | 見開きごとの補正（`dewarp`：`auto`/`off`、`margins`：`content_box`/`off`） | `{"op":"page_options","segment":"s0002","values":{"dewarp":"off"}}` |
| `image_only` | 文字認識に失敗したページを画像だけで残す | `{"op":"image_only","page":"s0044-L","value":true}` |
| `order` / `reset_order` | 出力順を指定する／撮影順に戻す | `{"op":"order","order":["s0001-L", "..."]}` |
| `rotate_video` | 動画のページを左に90°×k 回す | `{"op":"rotate_video","video":"v0001","k":1}` |

### 処理する

| 要求 | 内容 |
|---|---|
| `POST /api/run` `{"export":false}` | 変更を反映（変えたページだけ作り直してOCR）。`/api/job` の `running` が `false` になるまで待つ |
| `POST /api/export` `{"force":false}` | PDFを出力。要確認が残っているときは `force:true` が必要 |
| `POST /api/cancel` | 処理を中断 |

処理中（`running:true`）は `/api/action` を受け付けません。

### 選別のこつ（実際の本で効いたもの）

- ページ番号は、ページ画像の下の外側（左ページは左下、右ページは右下）の、高さ70〜97%あたりにあることが多い。その部分だけを切り出して並べると、数百ページでも番号を読み通せる
- 「重複として統合」された区間（`duplicate_of` あり）のほうがきれいで、採用された側がめくり途中ということがある。番号が抜けていたら、その前後の未採用区間を見る
- 背景が白い（シーツなど）と紙の範囲を取り違える。`mode=frame` で青い枠が見開きを囲んでいるかを見て、ずれていれば `geometry` で直す

## 処理の流れ

1. **動画の検査**（`vbs/video.py`）：拡張子ではなく中身で形式・回転情報・色特性を調べます。フレームは表示時刻PTSで扱うので、可変fpsにも対応します
2. **見開きの抽出**（`vbs/extract.py`）：縮小画像で約0.2秒前との差（動き量）を測り、秒単位の閾値で静止区間を見つけます。各区間から鮮明な候補を最大3枚選んで元解像度で取り出し、解析時の画像と同じ場面かを照合します。隣り合う区間は紙面どうしを位置合わせして比べ、同じ見開きなら重複としてまとめます（参照は残ります）
3. **分割と補正**（`vbs/split.py`）：紙面の範囲を検出し、綴じ目は文字のない帯と影から探します（中央に固定しません）。続いて傾き補正と照明ムラの補正を行います
4. **OCR**（`vbs/ocr.py`）：Tesseract（jpn）を使います。行の間隔から文字の大きさを推定し、OCR用の画像だけを1〜2倍に拡大して認識させます
5. **PDF**（`vbs/pdf.py`）：ページのJPEGを再圧縮せずに埋め込み、透明テキスト層を重ねます。確定した順で結合し、一時ファイルで検証してから置き換えます

各ページは「採用フレーム・設定・手修正」から計算した revision を持っています。revision が変わったページだけを作り直します。OCRも同じ仕組みで、ページ内容とOCR設定の組から作るキーで再実行を判断します。

合成動画での結果（1080p、文字高さ約21px）：

- 区間の抽出：正解の見開きすべてで過不足なし（可変fps、位置ずれによる重複を含む）

## 実写サンプルでの結果（市販の横書きの教科書、iPhone、4K HEVC、HLG、縦持ち、42.6秒）

実写の動画と、評価に使った検索語の表は、本の内容が写っているためリポジトリに含めていません。

- 見開きの抽出：14区間を検出。11見開きを採用し、手の持ち直しによる重複3組を統合。正解と一致
- 紙面の向き：本が画面の中で90°寝ていたのを、Tesseract OSDの多数決（5/5）で自動補正
- 紙面の検出：明るい木目の机と紙を、明るさと彩度で分離。紙の外（机・端から入る手）は白で塗る
- 裏写り：照明ムラの補正のあと、白レベル235で除去
- OCR：本文ページの平均信頼度は右ページ85〜90、左ページ65〜82（湾曲の影響）
- 処理時間：解析40秒、分割とOCRで約60秒（22ページ）
- PDF：22ページ・7.0MB。本文の語で検索できることを確認

レビューを受けた改修（2026-10-08）：

- 13ページ目の「行末の欠け」：調べた結果、欠けではなかった。行末で語の途中から次の行へ折り返しているだけで、元フレームでも行末から綴じ目までは白い紙だった
- 湾曲補正：行の中心線を多項式で近似し、画素を縦方向に動かして行をまっすぐにする。平均の曲がりが2.5px以上のページだけに適用（右ページは対象外になる）。本文の左ページの信頼度は 65〜82 → 77〜89。日付の数字の読み誤りも直った
- 透明テキスト層：Tesseractは日本語でも語ごとに空白を入れるので、TSVから配置し直して空白を除いた。Chrome・Edgeと同じエンジン（PDFium）で、空白なしのコピーと検索ができることを確認。Acrobatでは未確認
- 低信頼度ページの読み直し：信頼度70未満のページは、拡大率と区切り方を変えて読み直し、確かな文字が最も多い結果を採用する。扉ページの書名・著者名が検索できるようになった
- 余白：指の輪郭に沿って抜くのをやめ、内容の範囲の外を白に統一する。本文の中心部にかかる手は消さず「本文の範囲に手が重なっている疑い」として確認に回す。設定で無効にできる。元フレームはいつでも残っている

## 精度の評価と出力の検証

- `vbs verify プロジェクト [--terms 重要語.json]`：最後に出力したPDFをPDFium（Chrome・Edgeと同じエンジン）で開き直し、ページ数・文字層・重要語の検索結果をSHA-256と一緒に `出力名.verify.json` へ記録する。PDFの出力時にも自動で実行する（設定 `verify_terms` に重要語の表を指定できる）
- `tools/eval_real.py プロジェクト 重要語.json [--gt-dir 正解文の場所]`：固定したページを条件ごと（湾曲補正のあり・なし、読み直しのあり・なし）に作り直し、重要語の検出率を比べる。`正解文の場所/<ページID>.txt` があればCERも出す
- 重要語の表と正解文は本の内容から作るので、`samples/`（git管理外）に置く

実写サンプル（6ページ・重要語60語）での結果：

| 条件 | 重要語 |
|---|---|
| 採用中（湾曲補正あり・読み直しあり・白紙ページの足切り） | 53/60（最終PDFの検証でも53/60） |
| 湾曲補正なし | 51/60 |
| 読み直しなし | 49/60 |

注意：OCRの結果は、拡大率がわずかに違う（1.15と1.1538）だけで語単位で揺れる。1回の比較での±1〜2語の差は、改善とも悪化とも判定できない。

## 長時間・大量ページ・中断復旧

### 仕組み

- **メモリ**：元解像度の候補フレームは区間ごとに取り出して保存し、すぐ手放す。照合用の縮小画像はディスクへ追記する。重複判定は直前の区間の特徴量だけを持つ
- **途中保存**：動画解析の1回目（全フレームの走査）は20秒ごと、2回目（候補の保存）は1区間ごとに `jobs/` へ保存する。再開時は保存時刻の2秒前から読み直して重ねる。区間・フレームのIDは決まった順に振るので、再開しても連続実行と同じになる。manifest には全区間がそろってから反映する
- **OCR**：1ページ終わるごとに `ocr/<ページ>.result.json` を書く。再開時はそれを取り込み、終わったページを再実行しない。同時実行数（`ocr_workers`）と待ち行列（`ocr_queue`）に上限がある。時間切れ（`ocr_timeout_sec`、既定600秒）はスリープ中を数えない「起きていた時間」で測る
- **失敗の局所化**：1ページのOCR失敗・時間切れはそのページに記録して他を続ける（`--force` の出力では画像だけで残し、ページを落とさない。`image_only_pages` に記録）。自動の試し直しは2回まで。書き込み失敗・空き容量不足（`min_free_gb`、既定2GB）では新しい処理を始めずに止まり、終了コード3で理由を表示する
- **PDF出力**：`<名前>.new.pdf` に作って開き直して検証してから置き換える。PDFが開かれていて置き換えられないときは旧版を残し、新版の場所を表示する
- **後始末**：起動時に、このプロジェクトの画像を処理したまま残ったTesseractを終了し、書きかけの一時ファイルを消す

### 試験の実行

```bash
# 素材（元動画を再エンコードせずにつなぐ／長い静止を挟む／合成ページ）
.venv/Scripts/python -m vbs bench generate video --src samples/sample.MOV --minutes 30 --out work/bench/inputs/concat30.mov
.venv/Scripts/python -m vbs bench generate still --src samples/sample.MOV --at 11 --minutes 5 --out work/bench/inputs/still05.mp4
.venv/Scripts/python -m vbs bench generate pages --n 300 --out work/bench/inputs/pages300
# 計測（本番のCLIを子プロセスで動かし、プロセスツリーのメモリを5秒ごとに記録）
.venv/Scripts/python -m vbs bench run --video work/bench/inputs/concat30.mov --no-ocr
.venv/Scripts/python -m vbs bench run --pages work/bench/inputs/pages300 --workers 4
# 中断・再開（強制終了→再開の結果を連続実行と比べる）
.venv/Scripts/python -m vbs bench resume-test ocr-mid --video samples/sample.MOV
# まとめて
bash tools/bench_suite.sh resume
bash tools/bench_suite.sh endurance
.venv/Scripts/python tools/bench_report.py > work/bench/REPORT.md
```

結果は `work/bench/<実行ID>/result.json` に、環境（コミット・依存・モデルのハッシュ・PC）、入力のハッシュ、段階別の時間、メモリの推移、強制終了の位置、比較結果、最終PDFのハッシュと検証結果と一緒に残る。障害注入は環境変数 `VBS_FAULT`（`vbs/faults.py`）で、試験のときだけ有効になる。

| 動画解析の中断 | 1回目・2回目の走査中、ページ作成中に強制終了 | 再開結果（区間の時刻・採否・ページID・画像）が連続実行と一致（VFRの元動画、3分連結） |

| PDF出力の中断 | 一時出力の書き込み中に強制終了 | 旧版のPDFが残り、再実行で正常なPDFを作成。一時ファイルは残らない |
| 局所的な失敗 | 1ページだけOCRを時間切れにする | 他のページは続行、失敗ページは画像だけで残る、試し直しは2回で停止 |
| 書き込み失敗 | ページ画像の書き込みで失敗させる | 終了コード3で理由を表示して停止、project.json は壊れず、再開すると連続実行と一致 |

- **30分入力の通し（OCR・PDFまで）**：842ページ、OCR失敗0、最大 Private 2034MiB（OCR 4並列中）、PDFは842ページで検証済み。連結の各回のページを元動画単独の結果と照合し（`vbs bench concat-check`）、全42回で採用した見開き・ページ画像のハッシュが一致、最終PDFでの60語の検索結果も全回で元動画と同じ
- 10分と30分で最大メモリはほぼ同じ（1528/1537MiB）。解析中のメモリは前半・後半とも約1.37GiB→0.86GiBの同じ推移で、動画の長さに比例した蓄積はない。作業容量はページ数に比例して増える（出力そのもの）
- 30分入力の見開き数は 42×11−41＝421。連結点ごとに扉の見開きが「途中の短い静止」として採用されないため（連結点は人工的な切り替わり）
- 合成ページの期待語は 655/900。取りこぼしの多くは英数字コードで、日本語モデルが「0」を「O」と読む（例：Case B0137 → Case BO137）。合成画像の結果で、実写の精度の根拠にはしない

試験中に見つけて直した不具合：

- 蓋を閉じてスタンバイすると、OCRの時間切れを壁時計で測っていたため正常なページが失敗扱いになっていた → 起きていた時間で測る
- 再開時に途中保存ファイルを開いたままにしていて、Windowsでは次の保存で置き換えられなかった（WinError 5）
- プロジェクトを相対パスで指定すると、取り残されたTesseractを再開時に見つけられなかった → プロジェクトのパスを絶対パスにそろえる
- 長い静止が動画の大半を占めると、動きの閾値が下がりすぎて手持ちの見開きを取りこぼした → 60秒以上ほぼ動かない区間を閾値の推定から外す
- 障害注入の記録関数の引数名の衝突、イベント記録の読み取り位置のずれ（試験道具側）
- 候補フレームの取り出しで、シークが目的より後ろのキーフレームに着くと、そのフレームを黙って飛ばしていた（連結MP4で各回1件。回ごとの照合で発見）→ 手前から読み直す
- 「0.2秒前のフレーム」の判定が浮動小数の誤差で動画内の位置によって変わり、同じ映像でも代表フレームが入れ替わっていた（30分の照合で42回中17回しか一致せず発見）→ 比較に 1µs の余裕
- 色かぶりのある映像で紙を見失っていた（SmartDoc）→ 紙の色を基準にする（無彩色に近い映像は従来どおり）

## 既知の制限

- 湾曲補正は行の上下の曲がりだけを直します。綴じ目付近で文字が横に詰まるのは直せません
- OCRの既定はpsm6（ページ全体を1つのブロックとして読む）です。段組みや囲み記事が多いページでは読み順が混ざることがあります。その場合は設定で「自動（psm3）」を試してください
- 縦書き（jpn_vert）には対応していません。読む方向の設定でページの順序は右→左にできます
- 手が紙面に写っていても、静止していれば候補になります。確認画面で見てください
- 画面全体に強い色かぶりがあると、紙面の検出に失敗します（SmartDocのサンプルで確認）
- 日本語モデルは英数字の「0」を「O」と読むことがあります
